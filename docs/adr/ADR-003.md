# ADR-003 — Provider Adapter

| Field | Value |
|-------|-------|
| **ADR Number** | ADR-003 |
| **Title** | Centralize prompt generation in Provider Adapter |
| **Status** | Accepted |

## Context

Prompt building logic is scattered across `design-process`, `render-engine`, `prompt`, and the production handler.

## Problem

Prompt generation exists in multiple modules. Providers cannot be swapped without duplicating prompt logic.

## Alternatives

1. Keep per-module prompt builders (violates LAW-001)
2. Shared prompt utility library (still allows generation outside boundary)
3. **Single Provider Adapter** (accepted)

## Decision

Move all prompt generation into **Provider Adapter**. Only the adapter translates `RenderBlueprint` (+ provider mapping) into provider-specific prompts.

## Reason

One compiler boundary makes providers replaceable and enforces LAW-001.

## Consequences

**Positive:**

- Providers become replaceable
- One prompt compiler
- Testable mapping per provider

**Negative:**

- Migration effort from legacy prompt modules

## Migration

See Part 18 (Prompt module LEGACY), Part 19 Wave 04–07, RFC-004.

## Affected Files

- `src/lib/prompt/` → Provider Adapter
- `src/lib/design-process/` (remove Prompt Builder)
- `src/lib/render-engine/` (remove Prompt)

## Acceptance

Zero prompt generation outside Provider Adapter. Architecture validator enforces boundary.

## Rollback

Re-enable legacy prompt builders behind feature flag (violates stop conditions in Part 18/19).
